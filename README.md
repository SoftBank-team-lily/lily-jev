# lily-jev

## 지금 붙어 있는 곳

`lily-builder`가 `lily.remediate.enabled`이고 `JEV_API_KEY`가 있을 때 `code-defect`를 묻습니다. 예 확률 0.8 이상이면 diff를 만들고, 0.2 이하면 만들지 않습니다. 그 사이거나 호출이 실패하면 빈 값입니다. 키가 없으면 묻지 않고 코드 결함으로 봅니다. `lily-observer`는 이 클라이언트를 부르지 않습니다.

## 붙이기로 한 곳

아래 1·2·3은 builder·observer 코드에 아직 없습니다.

### 1. 이미지를 어떤 파일로 만들지 (lily-builder)

레포에 `pom.xml`, `build.gradle`, `package.json`처럼 빌드 파일이 둘 이상 있으면, 지금 규칙은 목록에서 먼저 보이는 파일로 Dockerfile을 만듭니다. 뒤에 있는 파일이 실제 앱이면 Kaniko 빌드 몇 분이 잘못된 이미지에 쓰입니다.

빌드 파일이 둘 이상일 때만 Jev에게 그 파일들 중 하나를 고르게 하기로 했습니다. Dockerfile이 이미 있거나 빌드 파일이 하나면 호출하지 않습니다. 온프레미스 에이전트는 이 결과를 잡으로 받습니다. 사용자 PC에는 API 키를 두지 않습니다.

### 2. 앱이 쓰는 데이터베이스 (lily-builder)

Gradle이나 package.json에 PostgreSQL 흔적과 MySQL 흔적이 둘 다 있으면, 규칙은 먼저 발견된 드라이버로 DB를 만듭니다. 잘못된 DB는 준비 실패나 다른 스키마로 이어집니다.

두 엔진이 같이 보일 때만 `postgres`와 `mysql` 중 하나를 묻기로 했습니다. 하나만 보이면 그 드라이버를 씁니다.

### 3. 롤백하기 전에 한 번 더 확인 (lily-observer)

에러율이 롤백 기준을 넘으면 규칙이 CRITICAL을 냅니다. 짧은 순간 5xx만으로 새 버전을 되돌리면, 문제 없는 배포가 내려갑니다.

CRITICAL일 때만, 앱마다 10분에 한 번, “지금 숫자를 보고 새 버전을 되돌릴 장애인가”를 묻기로 했습니다. 예일 확률이 0.2 이하이면 경고로 한 단계 내립니다. 그 사이이거나 호출이 실패하면 CRITICAL을 유지합니다. 그래서 애매할 때는 기존처럼 롤백 쪽으로 기울고, 확실히 순간 잡음일 때만 롤백을 멈춥니다.

## 넣지 않은 곳

| 모듈 | 이유 |
|---|---|
| 온프레미스 프록시, 클라우드 버스팅 | 요청마다 나누는 경로입니다. 호출 한 번이 로컬 처리보다 느립니다. |
| lily-cicd 슬롯 전환 | blue/green과 canary 비율은 이미 정해진 계산입니다. 틀리면 트래픽이 끊깁니다. |
| 온프레미스 에이전트 안의 스택 분석 | API 키를 사용자 PC에 두지 않습니다. 겹치는 파일과 DB는 builder가 잡에 실어 보냅니다. |
| lily-db-provisioner | 엔진은 배포 요청에 적힌 `postgres` 또는 `mysql`을 그대로 만듭니다. |
| lily-loadbalancer, lily-frontend | 판정보다 전달과 화면이 하는 일입니다. |

## 클라이언트

`com.lily.jev.Jev`가 호출 입구입니다. `HttpJev`는 `POST https://api.typesafe.ai/v1/systemone`으로 선택(`choice`) 또는 예/아니오(`noul`) 질문 하나를 보냅니다. 연결은 2초, 응답 대기는 4초입니다.

- 선택 답은 허용한 키이고 확신도가 0.8 이상일 때만 돌려줍니다.
- 예/아니오 답은 0에서 1 사이의 확률을 그대로 돌려줍니다.
- 키가 없거나, HTTP가 실패하거나, 확신도가 낮으면 빈 값을 돌려줍니다. 호출한 쪽은 기존 규칙을 유지하면 됩니다.
